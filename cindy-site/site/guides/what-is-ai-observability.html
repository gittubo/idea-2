Monitoring watches the machine, observability watches the decision

Normal software fails loudly. The page crashes, the API slows down, the database throws an error, and your monitoring lights up red. That is monitoring: it watches the machine.

AI fails quietly. The app is up, the response is fast, and the answer is just wrong. Nothing "breaks", so nothing turns red. Observability is different from monitoring because it watches the decision, not the machine: what the model was asked, what information it pulled in, what it actually replied, and whether that reply was any good.

the one word

The trace: the full journey of one answer

A trace is the step-by-step record of a single AI request, from the question to the final answer. When something goes wrong, you open that one trace and see exactly where it went sideways. Here is what a good trace captures.

  1. 💬 The input. The exact question the user asked, plus any system prompt or settings in play at the time.
  2. 📚 The context it retrieved. For a RAG or search app, the documents or data the model pulled in to answer. Most wrong answers start here, with the model retrieving the wrong thing.
  3. 🧠 The model call. The prompt actually sent, the model used, and the tokens, cost, and latency of that call.
  4. 📤 The output. The final answer the user saw, so you can compare it against what was retrieved.
  5. ✅ A score. An automatic check on whether the answer was faithful to the context, so you can filter for the bad ones without reading every single trace.
do it yourself

How to trace your own AI app, free

You do not need a paid platform to start. Pick one free tool, wrap your model calls, and you will see your first trace in an afternoon. Have Claude do the wiring with you:

🛠️ add tracing to your app 
I have a small AI app (a chatbot or RAG app) and I want to add tracing so I can see what happens inside each answer. Walk me through adding Langfuse to it step by step: whether to use the free cloud tier or self-host, where to get my API keys, and the exact code to wrap my model calls so every request logs the user's question, the context I retrieved, the model's answer, plus latency and token cost.

Then show me how to open one trace and actually read it. Assume I am not an experienced engineer, so explain each step, name the files I am editing, and do not skip the setup.

Then add a cheap automatic check so the bad answers surface themselves:

✅ add a faithfulness score 
Now help me add a simple faithfulness check to my traces. For each answer my AI gives, I want a second, cheap model call that reads the context I retrieved and the final answer, then scores from 0 to 1 whether the answer is actually supported by that context, with a one-line reason.

Show me exactly where to attach that score to the Langfuse trace so I can filter for low-scoring answers in the dashboard. That filtered list is my pile of silent failures, so explain how to read it and what to fix first.
the free tools

4 free observability tools worth knowing

Langfuse Open source, with a free cloud tier and a one-command self-host. Great default: tracing, evals, and cost tracking in one place.
Arize Phoenix Open source and fully free. Strong on visualising traces and running evals locally, no account needed to start.
LangSmith By the LangChain team, free developer tier. Easiest if your app is already built on LangChain.
Helicone Free tier, and the lightest lift: it sits in front of your model as a proxy, so you get logging by changing one line.
what to watch

The 4 signals that catch silent failures

Faithfulness Is the answer actually backed by what the model retrieved, or did it invent a policy that does not exist? This is the big one.
Retrieval quality Did it pull the right documents in the first place? A confident answer built on the wrong source is still wrong.
Latency and cost Slow, expensive answers quietly bleed money and users. Traces show you which step is the culprit.
User feedback A thumbs-down or a "that's not right" reply, tied back to its trace, so you can open the exact answer that annoyed someone.
You do not need to be an engineer to start. Add one tool, log your traces, and set up one faithfulness check. That single view of "answers my model got wrong" is worth more than any dashboard full of green.
