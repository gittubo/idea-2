the reality

Why proof beats paper right now

The job market genuinely did shift mid-degree, so this isn't in your head.

  • 📉 Recent computer science graduates are sitting at a 6.1% unemployment rate, higher than the 5.8% average across all recent grads, per the Federal Reserve Bank of New York's labor market data. Source: newyorkfed.org/research/college-labor-market
  • 🧊 Entry-level software engineering roles dropped roughly 30% year over year (Handshake 2025 data), and new-grad hiring at Big Tech is down more than 50% from 2019 levels. Source: techtarget.com/whatis/feature/Tech-job-market-statistics-and-outlook
  • 🛠️ The pattern hiring managers keep repeating in 2026: they don't hire you because you can follow a tutorial, they hire you because you can point at something live and say "I built that." Documented portfolios where the thinking and tradeoffs are visible are the signal that survives.

The takeaway isn't "the degree is worthless." It's that the degree was never the real asset. Shipped proof of what you can build is. So we're going to build the proof.

the setup

Step 1: install Claude Code and pick one real project

Claude Code is Anthropic's agentic coding tool that lives in your terminal (or IDE). It reads your whole project, edits files across the codebase, runs commands, and can plan a build before it writes a line. It's the tool that lets a non-senior person ship something real end to end. Docs: code.claude.com/docs/en/overview

  1. 💻 Install it on Mac, Linux, or WSL with the one-line installer, or on Mac with Homebrew (brew install --cask claude-code), then run claude inside any project folder: 
    curl -fsSL https://claude.ai/install.sh | bash
  2. 🎯 Pick a project that solves a real, specific problem, not a to-do app clone. Good picks: an internal tool that scrapes and summarizes something you actually check daily, a small dashboard for a hobby you have real data for, or a CLI that automates a boring task from your own life. A recruiter can tell the difference between "I followed a course" and "I needed this to exist."
  3. 🧠 Use plan mode before you build. Press Shift+Tab inside a session (or start with claude --permission-mode plan) so Claude reads the context and proposes a plan you approve before it touches any files. This is how you stay in control and actually learn the decisions instead of blindly accepting code. Source: code.claude.com/docs/en/common-workflows

The build prompt to paste into Claude Code:

🧰 the build prompt 
I want to build one real, portfolio-worthy project end to end that solves this problem: [describe the actual problem in 2-3 sentences]. Before writing any code, use plan mode: propose the smallest version that fully works, the tech stack, and why you'd choose it over the alternatives. Then build it step by step, explaining each key decision as you go so I can defend it in an interview. Keep the scope tight enough to finish, but real enough that it actually works.
the write-up

Step 2: turn the build into a real case study

A repo full of code is not a portfolio. The case study is what recruiters actually read. Claude can write it for you, but keep YOUR voice on the decisions.

📝 the case study prompt 
Look at everything we just built. Write a case study for my portfolio in this structure: (1) the problem and who it's for, (2) what the tool does, (3) the tech stack and why I chose it, (4) the three hardest decisions and the tradeoffs I weighed, (5) what I'd do differently at scale. Write it in first person, plainly, no fluff. Flag anywhere I should add my own reasoning so it sounds like me, not like AI.

The tradeoffs section is the part that gets you hired. Anyone can list features. Being able to say "I chose SQLite over Postgres because the dataset was small and I wanted zero setup for reviewers" is what signals you can actually think like an engineer.

the packaging

Step 3: README, demo script, and interview prep

This is the difference between a project nobody opens and one a recruiter can evaluate in 90 seconds.

🎤 README, demo and Q&A 
Write a clean README for this project: a one-line summary, a short "why I built this," a quickstart so anyone can run it in under 5 minutes, a screenshot placeholder, and a short "key decisions" section that explains the reasoning, not just the features. Then write a 60-second demo script I can record showing the tool working. Finally, list the 3 toughest questions an interviewer would ask about this build, and draft strong answers I can adapt in my own words.

A README that explains decisions ("why React over Vue, based on the tradeoff") consistently stands out over one that just lists features. That single section does a lot of the convincing before you ever get in the room.

go further

3 bonus prompts to run next

1 · the senior code review 
Review my finished project like a senior engineer doing a code review before I show it to recruiters. Point out anything sloppy, insecure, or that would raise a red flag, and fix the top 3 issues with me.
2 · resume bullets 
Turn this project into 3 resume bullet points using the "accomplished X, measured by Y, by doing Z" format, with real specifics from what we built. Then write a shorter one-line version for my LinkedIn headline.
3 · the portfolio site 
Help me spin up a simple one-page portfolio site that showcases this project: the case study, the demo, a link to the live repo, and a short bio. Keep it clean and fast, and explain how to deploy it for free.
pick your level

How to get the most out of it

🌱 If you're just starting don't try to build something huge. One small tool that genuinely works and is fully documented beats a half-finished ambitious project every time. Use plan mode so you understand each step instead of copy-pasting blindly.
🚀 If you're further along use subagents to keep your context clean while Claude explores, ship the project with real tests, and use Claude to draft the PR and commit history so your GitHub reads like a professional's. Then repeat the whole loop for a second project in a different domain.
the honest bit

One honest caveat

Claude Code can write most of the code, but the value in an interview comes from YOU being able to explain it. Don't ship a build you can't defend. Read the case study, understand the tradeoffs, and be able to answer "why did you do it this way" in your own words. The tool builds the proof faster, but the understanding has to be real, that's the whole point of proof over paper.
