the five from the reel

Start here, in the order I showed them

All five are either a one-word URL swap or a single keypress. Nothing to install, nothing to clone.

  1. 1 · GitDiagram, the repo draws itself Swap github.com for gitdiagram.com and the codebase becomes a visual map you can click into. On a popular repo it serves a cached picture, so press Regenerate if the date looks old.
  2. 2 · Gitingest, the whole repo as one text file Swap it for gitingest.com and you get one file you can hand straight to Claude. Use its include and exclude filters first: React came back at roughly 1.7 million tokens, which fits in no context window.
  3. 3 · gitmcp.io, so Claude stops inventing functions Swap it for gitmcp.io to plug the project's real documentation into Claude, so it stops making up functions that do not exist. It serves documentation, not code, so it works best on repos that ship an llms.txt.
  4. 4 · The full stop key, my favourite On literally any repo page, press . and VS Code opens right there in your browser. Once you are inside you can use the search feature and even add extensions. This is the one I use most.
  5. 5 · github1s Swap it for github1s.com for the same browser VS Code view with no sign-in needed, unlike the full stop key. Very large repos load slowly.
⚠️ Why the full stop key does nothing for some people. Two conditions. You have to be signed in to GitHub, and your cursor must not be sitting in a text box. Click blank space on the repo page first, then press it. If you would rather skip the sign-in entirely, that is exactly what github1s is for.
the part that makes it work

What to actually ask once the repo is in Claude

A whole repo pasted in with no question attached gets you a summary you did not need. Ask for the map first, then the specific thing, and make it cite the file every time so nothing gets invented.

Paste this after a Gitingest or Repomix dump
I'm pasting an entire GitHub repository below as a single file.

Before you explain anything, map it for me:
- Where does execution actually start, and what runs first
- The 5 to 7 modules that matter, and one line on what each one owns
- Anything that looks like configuration I would need to change to run this myself

Then answer this one question: where is [the feature I care about] handled?

Rules: quote the file path and the line range for every claim you make. If something is not in what I pasted, say "not in the provided code" rather than guessing. Do not summarise files I did not ask about.
🌱 Filter before you dump. Trim by folder or file type first, otherwise you spend the whole context window on lockfiles and test fixtures before Claude reaches the actual code.

10 URL patterns that open a repo up

?plain=1 Add it to any Markdown file URL and you get the raw source with clickable line numbers, so you can link one exact line of a README.
raw.githubusercontent.com Build the path yourself: /owner/repo/branch/path. Plain file, no HTML, perfect for curl or pasting into Claude.
.diff or .patch Add to any commit or pull request URL for the change as plain text. .patch also carries author and date, so it can be replayed with git apply.
/archive/refs/heads/main.zip The whole repo as a zip. No clone, no git installed.
codeload.github.com The direct download endpoint behind that zip, with no HTML redirect, so it behaves predictably inside a script.
/releases/latest A permanent link that always resolves to the newest release, so a bookmark or a tutorial never goes stale.
/releases/latest/download/<asset> A never-expiring download link for the newest build. Only works when the project names the asset the same way every release.
/find/<branch> Straight into the fuzzy file finder from the address bar, without loading the repo page first.
.atom on commits or releases /commits/main.atom, /releases.atom, /tags.atom. An RSS feed of a repo, no account and no notification spam.
deepwiki.com Swap github.com for it and get an auto-generated wiki plus a chat box you can question. Generated, so a brand-new repo can lag its latest commits.
2 of 8

6 ways into a real editor without cloning

The > key The full stop key's overlooked twin. Same editor, but it opens in a new tab so you keep the GitHub page you were reading.
github.dev Swap github.com for github.dev in any repo URL, or just type it. Browser VS Code, with search and extensions, free.
vscode.dev/github/owner/repo The same browser VS Code but served by Microsoft, which sometimes loads when github.dev is being slow.
githubbox.com Swap it in and the repo opens in CodeSandbox, running rather than just readable. Best on JavaScript and frontend projects.
stackblitz.com/github/owner/repo Boots the project in a browser-native Node environment, usually faster because it runs in your own tab.
Colab for notebooks Replace github.com with colab.research.google.com/github on any .ipynb and it opens runnable, with a free GPU.

10 ways to search like you built it

symbol: language:go symbol:WithContext. Finds where a thing is defined, not the thousand places it is mentioned. The highest-leverage one here.
path: path:*.txt, path:/src/**/*.js, path:unit_tests.
content: Matches inside file contents only, ignoring paths and filenames, so a search for a filename stops returning every import of it.
language: language:ruby OR language:cpp OR language:csharp.
repo: org: user: repo:github-linguist/linguist, org:github, user:octocat.
Regex between slashes /sparse.*index/. Escape a slash as /^App\/src\//.
Case-sensitive regex /(?-i)True/. Search is case-insensitive by default, which is why looking for True kept returning true.
Booleans and exact match sparse AND index, "fatal error" NOT path:__testing__. Quotes work inside qualifiers too.
NOT is:fork log4j NOT is:fork. Forks are the number one reason a search returns the same file forty times.
is:archived is:vendored is:generated Excluding vendored and generated code is what separates searching the project from searching its dependencies.
⚠️ Code search has three limits worth knowing before you decide it is broken. GitHub's own docs say you must be signed in to use code search, even for public repos. Results cap at 100, and only the default branch is searched. Files over 350 KiB and vendored or generated code are excluded entirely.

4 ways to search the conversation, not the code

linked:pr and linked:issue is:open linked:pr shows open issues that already have a fix in flight, so you stop reporting a bug someone is fixing.
reactions:>1000 The fastest way to find what a project's users actually care about. Pair it with sort:reactions-+1-desc.
comments:>100 state:closed comments:>100 surfaces the arguments, which is where the real design reasoning gets written down.
involves: and reviewed-by: type:pr reviewed-by:someone. Finds who the real gatekeepers of a project are.

4 keys that move you hands-free

b Opens blame view. The blame button is buried in a menu, the key is one tap.
t Activates the file finder. The fastest way into a file whose name you half remember.
y Expands the URL to its canonical form, pinning it to the exact commit, so the link you share never rots.
Command+K The command palette, then > for command mode. Inside a comment box it inserts a Markdown link instead, so use Command+Option+K there.
💡 These only fire when your cursor is not in a text box, so click blank space on the page first or you will just type the letter into a search field.
6 of 8

6 ways to see how the code got here

/compare/main@{2weeks}...main A time-based compare. What changed in the last two weeks, with no tags, no SHAs and no release notes. Swap in @{1day} or @{3months}.
/compare/v1.0...v2.0 The full diff between any two branches, tags or commits.
/commits/main/<path> The entire history of one file, which is how you find out why a weird line exists.
/commits?author=<handle> Everything one person changed in this repo.
View blame prior to this change The small icon inside blame that walks one line backwards past the commit that only reformatted it. This is the actual skill.
Line-range permalinks Click a line number, shift-click the last one, copy permalink. Paste it into an issue comment and GitHub renders the code inline. Comments only, not Markdown files.
7 of 8

6 ways to judge a repo before you trust it

/pulse GitHub's own one-page summary: commits, merged PRs, active contributors over a window. The fastest honest answer to "is this alive".
/graphs/contributors One person doing 95% of the commits is a risk that a star count completely hides.
/network/dependents Who else depends on this repo, with counts. Better proof than stars, because it is people shipping it rather than bookmarking it.
/forks?include=active&sort=stargazers The abandoned-repo rescue. When a project dies, its most-starred active fork is usually the maintained continuation.
/activity Shows force pushes, branch deletions and direct pushes to main, the things a plain commit list quietly hides.
api.github.com/repos/owner/repo No token, no sign-in. One JSON object with stars, licence, archived and pushed_at, so you check a repo's real state in one line.
8 of 8

4 ways to hand a whole repo to an AI

repomix.com Like Gitingest but it gives you token counts per file, include and exclude patterns, and it strips anything that looks like a credential before you paste. Also runs locally with npx repomix --remote <url>.
context7.com/<org>/<repo>/llms.txt The best thing on this page. A library's real documentation as clean LLM-ready text, free, no sign-in, every snippet linked back to its source file. Takes ?topic= and ?tokens=.
api.github.com/repos/owner/repo/git/trees/main?recursive=1 The entire file tree as JSON in one unauthenticated request. The cleanest way to show an AI a repo's shape without shipping it the code.
sourcegraph.com/search Free public code search that indexes well beyond GitHub, with real regex and structural search, and no sign-in for public code.
the honest bit

Three things worth knowing

  1. A whole repo will blow a context window. React came back from Gitingest at roughly 1.7 million tokens. Filter by folder or file type first, or use Repomix so you can see the token count before you paste.
  2. These URL swaps are third-party services. Whatever you point them at, they can see. Completely fine for public repos. Think twice before you point one at anything private or at client work.
  3. The generated views are generated, not authored. Diagrams and auto-wikis can lag the latest commits, so when the map and the code disagree, the code is right.
